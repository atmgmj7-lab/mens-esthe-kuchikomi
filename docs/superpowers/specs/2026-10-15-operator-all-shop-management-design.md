# Operator all-shop management — design

## Purpose and users

This is an operator work surface, not an analytics dashboard. Operators need to search every store, inspect its legacy identity and live publication, edit an isolated draft, attach private images, request/review changes, and publish only the approved projection. Partners remain limited to their own approved-listing workflow.

The chosen layout is a full-page searchable table with server pagination, followed by a detail/editor screen with an audit/review rail. It avoids initial loading of images, full histories, or every store.

## Data dictionary

| Data | Source of truth | Visibility | Notes |
| --- | --- | --- | --- |
| Legacy WordPress ID/slug/reviews | Existing WordPress | Read-only server import | Never rewritten by this feature. |
| Managed store identity | `private.managed_shops` | Service-only | Optional immutable legacy binding or newly generated directory identity. |
| Working content | `private.managed_shop_revisions` | Service-only | Immutable revisions: draft, submitted, changes requested, approved. |
| Publication | `private.managed_shop_publications` | Server read model | Only an approved revision is eligible for the public composition. |
| Assets | private Storage + `private.managed_shop_assets` | Service-only | Browser receives short-lived upload/served capability only through dashboard API. |
| Audit/reviews | `private.managed_shop_reviews` / audit log | Service-only | No personal login details or storage keys appear in UI. |

## State model

```text
legacy WordPress shop --(operator opens edit)--> imported managed identity + draft r1
new shop --(operator creates)---------------> managed identity + draft r1
draft --submit--> submitted --operator approves--> approved publication
submitted --request changes--> changes_requested --edit--> draft next revision
published projection remains unchanged for every draft/submitted/changes_requested state.
```

## Public composition

1. Fetch legacy WordPress shop/list/area data and published managed projections in bounded batches.
2. For a matching legacy binding, verify `(wp_shop_id, slug)` before overlaying only the managed publication fields.
3. For a managed record with no legacy binding, expose the managed projection using its directory ID and canonical slug.
4. Exclude any draft-only, withdrawn, identity-mismatched, or unapproved rows.
5. Use this identical composed model for `/shops/[slug]/`, `/shops/`, and area lists. Existing reviews stay associated with legacy IDs only.

## Fields

The initial operator payload is deliberately bounded: name, area name/slug, introduction, official URL, address, hours, phone, LINE URL, booking URL, basic price, 90-minute price, banner, gallery images, and publication intent. It does not edit reviews, rankings, WordPress taxonomies, canonical URLs, or user ownership.

## Security and concurrency

- Private tables have RLS enabled and privileges revoked from `public`, `anon`, and `authenticated`.
- Only narrowly scoped `api` RPC wrappers are granted to `service_role`; the browser never sees service credentials.
- `SECURITY DEFINER` functions use a fixed `search_path`, reject malformed identity/payloads, and compare expected revision under row lock.
- Asset object keys are generated by the server and validated against their managed store. Assets remain private and are served only after an approved-publication check.
- Operator Next routes require existing dashboard authentication, same-origin/CSRF checks, and return `private, no-store` / `noindex` responses.

## Dashboard IR

```yaml
page_purpose: Find and safely maintain store directory records.
users: [operator]
decisions: [import legacy identity, save draft, request changes, approve publication]
filters: [name, slug, area, source, publication state]
tables: [paged store directory]
drilldowns: [store identity, draft/public diff, assets, audit/review history]
empty_states: [no matching store, no managed draft, source unavailable]
data_requirements: [legacy WordPress read model, private managed directory, private asset capability]
performance_notes: [30 rows per page; fetch detail/history only after selection; no N+1 publication lookups]
review_checklist: [identity match, draft/public separation, revision CAS, actor authorization, asset ownership]
```

## Out of scope

- Bulk migration/import of existing production shops.
- Any production database migration, access-control change, user creation, plan/billing change, or deployment.
- WordPress writes, deletes, changing prefecture cards, and changing review ownership.
