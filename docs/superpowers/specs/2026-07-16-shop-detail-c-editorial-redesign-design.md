# 店舗詳細 C案「データ先行・編集型」再設計

作成日: 2026-07-16
対象: `headless/app/shops/[slug]/` の全店舗詳細ページ
停止条件: ローカル実装・検証完了後、push・本番公開前で停止

## 目的

店舗詳細ページの画像引き伸ばし、PC・スマホの表示崩れ、窮屈な横幅、内容の薄さを改善する。ユーザーが料金・駅・営業時間・予約先を短時間で確認でき、予約または公式サイトへ進みやすいページにする。同時に、店舗責任者が自店舗の情報を登録・修正したくなる、上品で分かりやすい導線を設ける。

主要指標は予約・公式サイトへのクリックとする。補助指標として店舗責任者向け登録・修正導線のクリックを計測する。

## 現状と進捗評価

現行ページには店舗名、料金、口コミ、基本情報、予約導線などの機能的な土台がある。一方で、次の理由から完成品質は約40%と評価する。

- 420×315程度の画像がPCで約806×1035まで拡大され、縦方向へ不自然に見える。
- `globals.css` 内の複数の店舗詳細用指定が同じ画像へ重なり、メイン画像とサムネイルの高さを上書きする。
- PCの実表示幅が約900pxに留まり、情報量に対して窮屈である。
- スマホでは上部情報が約872pxを占め、メイン画像と予約判断情報が初期画面に入りにくい。
- 382店舗中、本文0、抜粋0、画像241、公式URL333、確認可能料金252、AI要約76、住所候補49であり、情報量に差がある。
- 未入力値を12,000円、不定休、完全予約制、駐車場なし、0名などへ置き換える処理があり、確認できない内容を事実のように見せる危険がある。
- 現行の `OPEN` 表示は営業中であることを確認せず表示される。
- `ShopDetail.tsx` 約580行に、値の整理、表示、比較、口コミ、連絡導線が集中している。

## 採用するデザイン

ユーザー承認済みのC案「データ先行・編集型」を採用する。

- 角丸カードを並べない。
- 高級感は広い余白、細い罫線、明確な文字の強弱、写真比率で作る。
- PCの本文幅は最大1360pxとし、画面幅に応じて左右余白を保つ。
- スマホは左右16pxを最低余白とし、横スクロールを発生させない。
- 店舗名の直後に、存在する料金・駅・営業時間・予約方法を罫線区切りで表示する。
- 予約導線は上部とスマホ固定領域に置く。公式サイトと予約先が異なる場合は別ボタンにする。
- 店舗画像は原則4:3で表示し、CSSで縦方向へ引き伸ばさない。
- 情報量が少ない店舗でも空の枠を残さず、存在する情報だけで自然に詰まる構成にする。

## ページ構成

表示順は次のとおりとする。

1. パンくず。
2. エリア、店舗名、確認日。
3. 料金、最寄駅、営業時間、予約方法の概要。存在する項目だけ表示する。
4. 予約、公式サイト、電話、LINEの実在する導線。
5. メイン画像と追加画像。
6. 料金プラン。
7. 店舗紹介、特徴、設備。確認済み項目がある場合だけ表示する。
8. アクセス・基本情報・出典・確認日。
9. 承認済みユーザー口コミ。0件の場合は短い案内と投稿導線だけを表示する。
10. 同じエリアの比較ページなど既存内部リンク。
11. 店舗責任者向け登録・修正導線。

年齢層、平均料金比較、AI要約などは、出典と表示条件が満たされる場合だけ残す。未入力の0値や仮の平均値でグラフを作らない。

## 店舗独自コンテンツ

内容を増やすために文章を水増しせず、次の確認済み情報を店舗ごとに組み合わせる。

- 店舗責任者または公式サイトに記載された店舗紹介。
- 施術方針、空間、設備、支払い方法、予約方法。
- コース時間、料金、追加料金。
- 最寄駅、徒歩分数、出口、アクセス補足。
- 営業時間、受付終了、定休日。
- 公式写真と掲載許諾情報。
- 公式サイト、公式予約ページ、公式SNS。
- 項目別の出典URLと確認日。

推測、架空口コミ、出自不明文章、AIが作った体験談、根拠のないおすすめ表現は追加しない。AI要約を表示する場合もユーザー口コミとは分離し、出自を明示する。

## 公開データと申請データの境界

公開中の店舗詳細は引き続きWordPressを読む。Supabaseの非公開候補を公開ページへ自動表示しない。

| 区分 | 保存先 | 用途 |
|---|---|---|
| 公開店舗情報 | WordPress | 現在の店舗詳細、SEO、構造化データ |
| 調査済み移行候補 | Supabase非公開データ | 比較・審査・将来の切替候補 |
| 店舗責任者の申請 | Supabase非公開審査キュー | 登録・修正依頼の受付と審査 |

店舗責任者の申請が届いても、WordPressまたは公開viewを自動更新しない。公開判断と公開反映は別工程とし、別途承認を必要とする。

## 店舗責任者向け導線

店舗詳細の上部には控えめなテキスト導線、ページ末尾には濃緑の全幅案内を置く。

表示文言は「このページを、公式情報で完成させませんか？」を基準とし、次の価値を事実に限定して伝える。

- 公式の予約先を分かりやすく表示できる。
- 写真、料金、設備、店舗自身の紹介文を掲載候補として送れる。
- 確認日と出典を付けて情報の鮮度を伝えられる。

申請画面へは店舗ID、店舗名、slug、現在の店舗URL、遷移元を引き継ぐ。申請者は次を入力する。

- 氏名、役職、店舗との関係。
- 確認用メールアドレス。
- 修正対象。料金、営業時間、アクセス、予約先、店舗紹介、特徴・設備、写真から複数選択。
- 変更内容。
- 根拠となる公式URL。
- 個人情報の取り扱い、情報の正確性、画像掲載権限への同意。

初回実装では画像ファイルの直接アップロードを行わない。公式画像URLを受け取るか、申請後に運営が安全な方法で受領する。Supabase Storage、ファイル検査、削除期限、画像権利管理を同時に追加しないためである。

## Supabase申請保存の安全条件

申請はNext.jsのサーバー側APIを経由し、ブラウザからSupabaseへ直接書き込まない。

- 保存先は公開店舗テーブルと分離した非公開審査キューとする。
- RLSを有効にし、`anon` と `authenticated` にSELECT、UPDATE、DELETEを許可しない。
- ブラウザへservice roleまたはsecret keyを渡さない。
- サーバー側で必須項目、文字数、URL、店舗ID、選択項目、同意を検証する。
- honeypotと送信回数制限を適用する。
- エラー本文、ログ、アクセス解析へ氏名とメールアドレスを送らない。
- 実装前に現在のSupabase changelog、Data API公開schema、RLS、サーバー接続方式を公式資料で再確認する。
- 本番migration、Secret登録、本番保存試験は今回行わない。

安全なサーバー接続方法が現在の環境で確定できない場合、権限を緩めて代替しない。申請UIと既存お問い合わせへの安全なフォールバックまでに留め、Supabase保存は阻害条件として報告する。

## 実装構成

`ShopDetail.tsx` はページ順序とSEO情報の組み立てへ役割を絞る。表示値の整理とUIを次の単位へ分ける。

| 単位 | 役割 |
|---|---|
| `shop-detail-view-model` | 表示可能な料金、駅、営業時間、予約先、特徴、出典、確認日を整理する |
| `ShopHero` / `ShopFactsLedger` | 店舗名、概要、上部予約導線 |
| `ShopGallery` | 4:3メイン画像、追加画像、代替画像 |
| `ShopPriceSection` | 確認済み料金だけを表形式で表示 |
| `ShopFeatureSection` | 確認済みの店舗紹介、特徴、設備 |
| `ShopInfoSection` | アクセス、基本情報、出典、確認日 |
| `ShopActions` | 予約、公式、電話、LINEとスマホ固定導線 |
| `ShopOwnerCta` | 店舗責任者向け登録・修正導線 |

店舗詳細のスタイルは専用CSS Moduleまたは同等の局所スタイルへ移し、`globals.css` の既存汎用指定から影響を受けにくくする。既存のパンくず、LocalBusiness構造化データ、地域内部リンク、口コミ投稿導線、広告・PR関係属性は維持する。

## 情報不足・異常時の表示

| 状態 | 表示 |
|---|---|
| 店舗画像なし | 共通代替画像を4:3で表示する |
| 画像読込失敗 | レイアウトの高さを維持し、代替画像または背景へ切り替える |
| 料金なし | 料金概要と料金表を省略する。公式URLがあれば公式確認を案内する |
| 平均料金なし | 平均比較を表示しない。12,000円で補わない |
| 営業時間・定休日なし | 該当項目を表示しない。OPENや不定休を作らない |
| 年齢・設備なし | セクションごと表示しない。0名や駐車場なしを作らない |
| 口コミなし | 短い0件案内と投稿導線だけを表示する |
| 予約URLなし | 電話、LINE、公式など実在する導線だけを表示する |
| 外部URL不正 | ボタンを表示せず、ページ表示は継続する |
| 申請送信失敗 | 入力を保持し、再送できるエラーを表示する |

## クリック計測

既存GA4の外部リンク計測を拡張し、次のイベントを区別する。

| イベント | 主な値 |
|---|---|
| 予約クリック | shop slug、配置、電話・LINE・Web予約の種類 |
| 公式サイトクリック | shop slug、上部・本文・固定バーの配置 |
| 店舗責任者導線クリック | shop slug、上部・末尾の配置 |
| 店舗責任者申請完了 | 申請種別、遷移元。氏名、メール、本文は送らない |

既存の `official_site_click` と二重送信しないよう、アンカーのdata属性を基準に1回だけ分類する。

## レスポンシブ・操作性基準

- PC確認幅: 1440px、1280px、1024px。
- スマホ確認幅: 390px、375px、320px。
- PC本文幅: 最大1360px。
- スマホ左右余白: 最低16px。
- タップ領域: 44px以上。
- メイン画像: 原則4:3。`width: 100%` と `aspect-ratio` を使い、縦横両方の強制寸法を重ねない。
- 表はスマホで横スクロールさせず、行表示へ変形する。
- スマホ固定導線は本文を隠さないよう下余白を確保する。
- `focus-visible`、見出し順、リンク名、画像代替文を維持する。
- 色だけで予約種別や状態を区別しない。

## テスト方針

テストを先に追加し、現行実装で意図した失敗を確認してから修正する。

1. 仮の12,000円、不定休、完全予約制、駐車場なし、0名、静的OPENを禁止する検査。
2. 存在する値だけで概要列と基本情報行を作るview model検査。
3. 画像比率、メイン画像とサムネイルの個別指定、最大幅、スマホ余白のCSS契約検査。
4. 予約・公式・電話・LINE・責任者導線の表示条件検査。
5. GA4イベントが1クリックにつき1種類・1回になる分類検査。
6. 店舗責任者申請の入力検証、honeypot、回数制限、非公開権限検査。
7. 既存の料金正規化、出自分離、口コミ、PR、schema、内部リンク、最終デザイン検査を新構成へ更新。
8. lint、typecheck、全テスト、production build。
9. 情報充実店舗、画像なし店舗、料金なし店舗をPC・スマホで実画面確認する。
10. 横スクロール、壊れた画像、重なり、固定導線による本文隠れがないことを確認する。
